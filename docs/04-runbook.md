# 四、演练手册：一次完整的手机应急

> 这是「我接下来要做什么」的完整计划。你可以先通读一遍，再决定什么时候开始。
> 标 **【你做】** 的是你的动作，标 **【我做】** 的是我在这边执行。

---

## 剧本梗概

```
【我做】 偷偷推一个坏改动到 main（模拟同事误操作，绕过了 PR）
   ↓     CI 会绿灯放行，因为测试没覆盖到那个分支 ← 这是全篇最重要的一课
   ↓     CD 照常部署，线上开始算错钱
【你做】 手机打开页面，发现 9.9 元的单被减了 20
【你做】 手机上开 issue，@claude 描述现象
   ↓     云端虚拟机启动，AI 读代码、定位、写失败测试、修、开 PR
【你做】 手机上看 diff、看 CI 绿勾、点 Merge
   ↓     CD 自动跑，重新部署
【你做】 手机刷新页面，版本号变了，金额对了
```

---

## 第 0 幕：准备 —— 配 DeepSeek 密钥 **【你做】**

**为什么要你自己配**：API Key 不应该经过对话传递。你自己加，我全程看不到它。

1. 去 https://platform.deepseek.com/ 拿一个 API Key
2. 加到仓库密钥里，两种方式任选：

   **网页（手机也能操作）**
   ```
   https://github.com/niking314/test_gitaction/settings/secrets/actions
   → New repository secret
   → Name: DEEPSEEK_API_KEY
   → Secret: 粘贴你的 key
   ```

   **命令行**（在本会话里前面加 `!` 执行，它会隐藏输入）
   ```
   !gh secret set DEEPSEEK_API_KEY --repo niking314/test_gitaction
   ```

3. 配好后告诉我，我会先发一条**冒烟测试**（在一个无关紧要的 issue 里 @claude 说句话），确认这条链路真的通了，**再**开始制造事故。

> ⚠️ **诚实提示**：`claude-code-action` + DeepSeek 兼容端点这个组合，Anthropic 官方没有测试过。
> 协议层是通的（DeepSeek 专门提供了 `/anthropic` 端点给 Claude Code 用），但首次运行可能遇到两类问题：
> - **报缺少凭证** → 改成把 key 传给 `anthropic_api_key` 输入项，而不是走 env
> - **模型名不对** → 在 workflow 里显式设 `ANTHROPIC_MODEL`
>
> 这就是我坚持先冒烟测试再造事故的原因——不然事故造出来了，修事故的工具却是坏的。

## 第 1 幕：制造事故 **【我做】**

我会直接 push 到 main，**故意绕过 PR**——真实事故里这种「紧急改一下，来不及走流程」太常见了。

改动只有一行，在 `src/pricing.js`：

```diff
   if (coupon.type === 'full_reduction') {
-    // 没到门槛就不能用券
-    return subtotal >= coupon.threshold ? coupon.amount : 0;
+    return coupon.amount;
   }
```

**后果**：满减券丢掉了门槛判断，变成无条件减 20。买一杯 9.9 元的咖啡：

| | 正确 | 事故后 |
|---|---|---|
| 商品小计 | ¥9.90 | ¥9.90 |
| 优惠 | ¥0.00 | **-¥20.00** ← 券根本不该生效 |
| 运费 | ¥12.00 | ¥12.00 |
| **应付** | **¥21.90** | **¥1.90** ← 每单少收 20 元 |

**为什么 CI 会放行**：现有 6 个测试里，测满减的那条用的是 399 元的键盘（超过 100 门槛），改动后**结果不变**，测试照样绿。
**「小额订单 + 满减券」这个分支根本没有测试覆盖。**

> 🔑 **这是全篇最重要的一课**：
> CI 绿只证明「你写过的测试没挂」，不证明「代码是对的」。
> 真实世界绝大多数线上事故，都发生在测试的盲区里。

## 第 2 幕：发现 **【你做】**

用**手机浏览器**打开：**https://niking314.github.io/test_gitaction/**

页面上「挂耳咖啡」默认 1 件，优惠券选 **SAVE20**。你会看到：

- 优惠那行显示 **-¥20.00**（明显不对，才买 9.9 的东西）
- 页面弹出红色告警：**⚠️ 计价异常 —— 优惠 ¥20.00 超过了商品小计 ¥9.90**

那个红框是我在 `app.js` 里写的**线上兜底自检**。真实系统里这类断言应该上报到监控平台并触发告警；这里为了让你手机上一眼能看见，直接画在页面上了。

顺手记一下页面顶部的**版本号**，待会儿要用它确认修复真的上线了。

## 第 3 幕：派活 **【你做】**

手机上打开 GitHub App（或浏览器）→ 仓库 → Issues → New issue。

标题和正文可以直接抄这个：

> **标题**：线上计价错误：小额订单也能用满减券
>
> **正文**：
> ```
> @claude
>
> 线上 https://niking314.github.io/test_gitaction/ 算错钱了。
>
> 现象：购物车里只有 1 件 9.9 元的挂耳咖啡，选 SAVE20（满100减20）这张券，
> 优惠居然生效了，减了 20 元，应付变成 1.9 元。正确应该是 21.9 元（券不该生效）。
>
> 影响：所有低于 100 元的订单每单少收 20 元。
>
> 请定位是哪次提交引入的，修复，并补上能复现这个 bug 的测试。
> ```

**写 issue 的三个要点**（这决定了 AI 干得好不好，和带新人一模一样）：

1. **说现象，不说猜测的原因** —— 「9.9 元的单被减了 20」比「满减判断写错了」好。你猜错了会把它带沟里。
2. **给可复现的具体输入** —— 「1 件 9.9 元 + SAVE20」，而不是「小额订单」。
3. **说清期望值** —— 「应该是 21.9」。没有期望值它只能猜。

发出去之后，云端就开始跑了。你可以在 Actions 页面看它的进度，也可以直接等——它干完会在 issue 里回复。

`CLAUDE.md` 里那些规矩（必须先写失败测试再修、PR 描述要写现象/根因/改法/测试、用中文）它会自己读，你不用在 issue 里重复。

## 第 4 幕：Review 和合并 **【你做】**

AI 会开一个 PR。手机上打开它，检查四件事：

| 看什么 | 怎么判断 |
|---|---|
| ① **CI 绿勾** | 页面下方 checks 全绿。红的直接打回 |
| ② **diff 大小** | 应该只改 `pricing.js` 一行 + `pricing.test.js` 加几行。**改了一堆无关文件就是危险信号** |
| ③ **有没有新测试** | 必须有一个专门测「小额订单 + 满减券」的用例 |
| ④ **PR 描述** | 现象/根因/改法/新增测试，四样齐不齐 |

有问题就在 PR 里 **@claude 再说一句**，比如「你顺手改的那个函数跟这个 bug 无关，请去掉」。它会继续改同一个 PR。

**验证修复真的有效的小技巧**：点开 PR 的 Files changed，找那个新增的测试。
如果它写得对，这个测试在旧代码上必然失败、在新代码上才通过——这就是「回归测试」的意义：**这个 bug 从此不可能再回来**。

确认无误 → 点绿色的 **Merge pull request**。

---

## 第 5 幕：验证恢复 **【你做】**

合并瞬间触发 CD。等约 30-60 秒，然后：

1. 手机刷新 https://niking314.github.io/test_gitaction/
2. **看版本号变了没有**（对比你在第 2 幕记的那个）——号没变说明还是旧版本，缓存或部署没完成，再等等
3. 号变了之后，重新选 SAVE20：优惠应该是 **¥0.00**，应付 **¥21.90**，红色告警消失

**到这里，一次完整的线上事故就在手机上处理完了。**

## 第 6 幕：复盘 —— 你实际学到了什么

| 环节 | 背后的能力 |
|---|---|
| 坏代码直推 main | 为什么需要**分支保护**（下面有配法） |
| CI 绿但线上错 | **测试覆盖率盲区**，CI 不是万能的 |
| 页面红色告警 | **线上自检/监控**比 CI 更贴近真相 |
| 一句话派活 | 事件驱动 + 云端按需启动 |
| 手机看 diff | Review 的本质是**看改动范围**，不是逐行读代码 |
| 合并即上线 | CD 传送带 |
| 版本号确认 | **可观测性**——别信「应该好了」，要亲眼看见 |

### 演练完立刻该做的一件事：加分支保护

这次事故的根源是「能直接推 main」。补上：

```
https://github.com/niking314/test_gitaction/settings/branches
→ Add branch ruleset → 目标 main
→ 勾 Require a pull request before merging
→ 勾 Require status checks to pass → 选中 "单元测试"
```

配完之后，**任何人（包括你自己、包括 AI）都不能直接推 main**，必须走 PR 且 CI 必须绿。
这是投入产出比最高的一条规则，5 分钟配完，挡掉一整类事故。

## 附 A：如果 DeepSeek 那条链路没跑通

演练的价值不全在 AI 那一段。降级方案：**我来扮演「远程的 AI」**——我在这边分析、修复、开 PR，你在手机上 review + merge + 验证。

第 2、4、5 幕你的操作**完全一样**，只有第 3 幕从「@claude」变成「跟我说一声」。
CI/CD、通知、review、合并、自动部署、版本确认这些核心肌肉记忆，一个都不少。

之后你随时可以补上 AI 那一环——工作流文件已经在仓库里了，只差一个能用的密钥。

## 附 B：安全边界（公开仓库尤其要看）

仓库是 public 的，任何人都能提 issue。会不会有人 @claude 让它干坏事？

- **`claude-code-action` 默认只响应有写权限的用户。** 路人的 @ 会被忽略。
  （要放开得显式配 `allowed_non_write_users`，那个输入项在官方文档里明确标着 ⚠️ RISKY，别碰。）
- **fork 来的 PR 拿不到 secrets**，这是 GitHub 的硬性安全设计。
- `--max-turns 25` 限制单次最多干多少轮，防止跑飞了烧钱。
- **配了分支保护之后，AI 也只能开 PR，不能直接改 main。** 最终那一下永远是人点的。

**「AI 能改代码」和「AI 能上线」是两件事，中间那道 PR + 你的手指，就是安全边界。**
